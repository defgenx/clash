# CLAUDE.md — clash Project Guide

## What is clash?

Terminal UI for managing Claude Code Sessions & Agent Teams. Built in Rust with ratatui.

## Quick Commands

```bash
cargo build --release      # Build
cargo test                 # Run all tests (unit + integration)
cargo run -- --data-dir /path/to/test/data  # Run with test data
cargo run -- --debug       # Run with debug-level logging
```

## Before Pushing

**Always run format and linter before every push:**

```bash
cargo fmt                  # Auto-format code
cargo clippy               # Run linter
```

CI runs `cargo fmt --check` and `cargo clippy` — pushes will fail if either has issues.

## Documentation Rules

Every change **must** keep documentation in sync:

1. **README.md** — Update keybindings, commands, features, or behavior descriptions whenever they change.
2. **Guided tour** (`src/infrastructure/tui/widgets/tour.rs`) — Every new user-facing command or keybinding must be added to the appropriate tour step.
3. **Help overlay** (`src/infrastructure/tui/widgets/help_overlay.rs`) — Every new keybinding or command must appear in the `?` help screen (global, context, or commands section).

If a PR adds a keybinding but doesn't update all three, it is incomplete.

## Architecture: Clean Architecture (strict layers)

```
Infrastructure → Adapters → Application → Domain
(outer)                                   (inner)
```

**Dependencies point inward only.** Inner layers never import from outer layers.

### Layer Map

| Layer | Path | Purpose | May depend on |
|-------|------|---------|---------------|
| **Domain** | `src/domain/` | Entities (`Team`, `Task`, `Member`, `InboxMessage`, `TaskStatus`) and the `DataRepository` port trait | Nothing |
| **Application** | `src/application/` | `AppState`, `Action` enums, `Effect` enum, pure `reducer`, `NavigationStack` | Domain |
| **Adapters** | `src/adapters/` | `input.rs` (KeyEvent→Action), `renderer.rs` (State→Frame), `views/` (TableView/DetailView impls) | Application, Domain |
| **Infrastructure** | `src/infrastructure/` | `app.rs` (event loop), `fs/` (FsBackend, atomic writes, watcher), `tui/` (widgets, theme, layout), `windowing/` (pane/tab/window spawning, standalone attach client), `config/` (schema, layers, migrations, write path), `error.rs`, `event.rs` | All layers |

### Key Files

- `src/domain/entities.rs` — All domain types with lenient serde (`#[serde(default)]` + `#[serde(flatten)]`)
- `src/domain/ports.rs` — `DataRepository` trait definition
- `src/application/reducer.rs` — **Pure function** `fn(state, action) → (state, effects)`. No IO. All business logic lives here.
- `src/application/effects.rs` — Abstract effects (`PersistTask`, `CreateTeam`, `RemoveTeam`). No file paths — infrastructure translates these to real IO.
- `src/application/actions/mod.rs` — Nested action enums: `Nav`, `Table`, `Team`, `Task`, `Agent`, `Ui`
- `src/infrastructure/app.rs` — Event loop coordinator. Executes effects by calling the `DataRepository` impl. Session refresh is a thin call to `session_refresh`.
- `src/infrastructure/session_refresh.rs` — Pure session refresh pipeline: gathers input (disk, hooks, daemon), builds a complete sorted session list via `build_session_list()` (no IO), then swaps atomically into `DataStore`.
- `src/infrastructure/fs/backend.rs` — `FsBackend` implements `DataRepository`
- `src/infrastructure/fs/atomic.rs` — `write_atomic()`: write to temp file, then rename (prevents partial reads)
- `src/infrastructure/config/` — the config subsystem. `schema.rs` is the single source of truth (one `PROPS` table driving defaults, validation, the JSON Schema, `--defaults`, the GUI migration and the frontend live-apply hints); `layers.rs` merges defaults ← user ← project ← env with per-key provenance (pure); `migrate.rs` holds both migrations (flat v1 → namespaced v2, and the GUI settings blob); `doc.rs` + `lock.rs` are the write path. `ConfigHandle` is the **only** runtime accessor — see the config gotcha below
- `src/infrastructure/windowing/terminal_spawn.rs` — Terminal detection, smart pane/tab/window spawning with layout planning
- `src/infrastructure/windowing/attach.rs` — Shared attach loop (`attach_loop`) and standalone `clash attach <id>` client. Uses `/dev/tty` for input and `nix` termios for raw mode (avoids crossterm's reader thread)

## Core Pattern: TEA (The Elm Architecture)

```
User Input → Event → handle_key() → Action
                                      ↓
                            reducer::reduce()  ← pure, no IO
                                      ↓
                            (State', Vec<Effect>)
                                      ↓
                            execute_effects()  ← infrastructure IO
                                      ↓
                            renderer::draw()   ← reads state, draws frame
```

The reducer **never** touches the filesystem, network, or terminal. It returns `Effect` values that the infrastructure layer executes.

## Data Model

clash reads from Claude Code's filesystem:

```
~/.claude/
├── teams/{name}/config.json          # Team config + members[]
│   └── inboxes/{agent}.json          # InboxMessage[]
├── tasks/{team-name}/{id}.json       # Task with status, owner, dependencies
└── clash/scratch/{…tree}            # Scratches: a nested tree of free-form text files and folders (dir configurable)
```

All types use `#[serde(default)]` so missing fields get zero values, and `#[serde(flatten)]` captures unknown fields for forward compatibility.

Configuration is a separate, layered store: `<config_dir>/clash/config.toml`
(namespaced `[general] [paths] [sessions] [terminal] [notifications]` +
`[[ides]]`, with `[keymap]`/`[actions]` reserved for later phases and preserved
untouched), merged over in-code defaults and under a restricted repo-local
`<repo>/.clash/config.toml` and `CLASH_*` env overrides. `clash config` prints
the path, the merged result with per-key provenance, the annotated defaults, a
validation report, or the JSON Schema.

Scratches are an exception: the file on disk *is* the note (no structured JSON), so `ScratchNote` is a runtime view DTO built from the filesystem listing. They form an IntelliJ-style **tree** of files and folders: `load_scratch_notes` walks the scratch dir recursively and returns a depth-first **pre-order** flattening (folders first, alphabetical) where each node carries `id` (POSIX path relative to the scratch root — the stable identifier), `parent`, `depth`, and `is_dir`. `DataRepository` exposes `load_scratch_notes` plus the tree ops `create_scratch_note(parent, title)`, `create_scratch_dir(parent, name)`, `rename_scratch(id, new_name)`, `move_scratch(id, new_parent)` (cycle-guarded), and `delete_scratch_note(id)` (recursive for folders). Path safety is enforced by `sanitize_component`/`sanitize_rel_path` (reject separators/`..`, so nothing escapes the root). The pure `visible_scratch_indices(notes, expanded)` (in `application::state`) computes which rows are visible given the expanded-folder set, and is shared by the reducer (selection clamping) and both renderers. The TUI renders the tree via the custom `render_scratch_table` (not the generic table path) and supports create/rename/move/delete + expand-collapse. Moving goes through the core like every other op: `m` opens a folder picker (`UiAction::EnterMoveScratchMode` builds the candidate list via `scratch_move_targets` — root + every folder minus the entry, its descendants, and its current parent), the pick dispatches `ScratchAction::Move { id, new_parent }` → `Effect::MoveScratch` → `move_scratch`. The GUI instead reorganizes by drag-and-drop, calling the Tauri scratch command directly (bypassing the reducer/effects) — so the GUI path does not emit `ScratchAction::Move`, but the variant and effect now exist for the TUI. `y` copies an entry's path (IntelliJ-style "Copy Path/Reference…"): `UiAction::EnterCopyScratchPathMode` opens a picker (absolute `note.path` / relative `note.id` / file name), and the pick emits `Effect::CopyToClipboard { text }`, executed by `infrastructure::clipboard::copy` — best-effort platform command (`pbcopy`/`wl-copy`/`xclip`/`xsel`/`clip`) plus an OSC 52 escape (so it works over SSH and in clipboard-capable terminals; `base64` is already a dep, no new crate). The GUI mirrors the same three formats in the scratch-tree right-click menu (`noteContextMenu` → `copyScratchPath`), but writes directly via the `clipboard_write_text` Tauri command (like its other scratch ops) and confirms with a `flashToast` — it does not go through the reducer/effects. Both frontends open a scratch via the IDE/editor picker (`ide::detect_editors`): terminal editors run in a pane/tab, GUI editors launch alongside — so the backend never reads/writes note *contents*, only lists/creates/renames/moves/deletes entries. The scratch directory defaults to `<claude_dir>/clash/scratch` but is overridable via `config.toml`'s `scratch_dir` (resolved by `Config::scratch_dir`, held on `FsBackend` with interior mutability so the GUI Settings panel can change it live via `set_scratch_dir`, which persists through `ConfigHandle::set_json`).

**Workflows** are a second structured store, deliberately independent of scratches: `<workflows_root>/<project>/<slug>/{meta.json, plan.md, review.md, agent-review.md, annotations.json, history/<NNN>/}` manages a plan → plan-review → changes-requested → implementing → diff-review → pr-draft → pr-ready → done pipeline per item (statuses kebab-case in `meta.json`; `abandoned` from anywhere, `reviewing` as a returning side-trip). **The `pr-*` stages are optional**: approving at `diff-review` may go straight to `done`, because requiring a draft PR to approve strands every repo that merges to its default branch without one — the GUI therefore always offers `✓ Approve → done` and treats the PR path as primary only when a PR already exists. The root defaults to `<claude_dir>/clash/workflows`, overridable via `config.toml`'s `workflows_dir` (same interior-mutability pattern as `scratch_dir` — changing the scratch dir never moves workflows). Domain types live in `src/domain/workflow.rs` behind the separate `WorkflowRepository` port (kept off `DataRepository` to keep it minimal; GUI-only in v1, so the port and its `fs::workflows` impl carry documented `#[allow(dead_code)]` for the private-`mod` bin build); pure logic (slugify, FNV-1a `line_hash`, annotation anchoring, `AttentionLedger`) in `src/application/workflow.rs`; unified-diff parsing (one walk, structural + display views) in `src/application/diff.rs`; the `git diff` subprocess in `infrastructure::git::git_diff(dir, DiffBase)`; PR operations behind the **forge port** (`domain::forge::Forge` — view/create-draft/mark-ready/comment/unanswered-count/URL-parse/caps; `GithubForge` wraps the `gh` CLI transport in `infrastructure::gh`, `NoForge` makes forge-less repos explicit, selection = `workflows.forge` setting `auto|github|none` where auto detects from the origin remote host, cached per repo on `GuiState.forge_cache` — unknown hosts deliberately count as GitHub so GHE keeps working; only recognizably-gitlab/bitbucket hosts map to none until they have an impl). The GUI drives everything through `gui/src-tauri/src/workflows.rs` Tauri commands (the scratch-command pattern — no reducer/effects in v1). Key invariants: `(project, slug)` = the directory path is the identity; the agent and clash co-edit the files under a phase-ownership split (the agent may write `annotations.json` only during changes-requested/implementing/**reviewing** — the GUI locks its editor then; `history/`, `iteration` and `reviewRound` are clash-only, bumped in ONE meta write after the snapshot so partial failures abort cleanly); annotations re-anchor by trimmed-content hash when diffs drift and are never dropped (orphan tray); the `AttentionLedger` pre-seeded by every mutating command means only *agent* writes produce notifications; `refresh_workflow_pr` writes meta only on actual change so PR polling never churns the FS watcher. The agent-side file contract is `docs/workflows.md`, implemented by **four** embedded skills — `clash-workflow` (executor: plan/revise/implement/pr), the two self-contained reviewers `clash-plan-review` (judges `plan.md`; derived from the public `plan-review` skill including its per-issue interactivity) and `clash-code-review` (judges the diff; `Depth:` tunes rigor inside the skill), and `clash-explain` (the explainer: a review-shaped round — target `structure`, launched only by the explicit **◫ Explain changes** action, never derived — that judges nothing and overwrites `structure.md`, the Structure tab's document: functional parts, mermaid diagrams, risks, reading order; it still appends a `## Review N — structure` entry to `agent-review.md` so toasts/strip/Timeline stay truthful; mermaid renders via a lazy-loaded `gui/dist/vendor/mermaid.min.js` — 2.7MB parsed only when a doc actually contains a fence). The separations are deliberate: executor vs reviewer because a reviewer that may rewrite what it reviews has reviewed nothing, plan vs code review because one skill doing both jobs describes neither, explainer vs reviewer because explanation must stay judgement-free to be trusted (the old `clash-review` harness that delegated diff judgement to the `/code-review`//`/review` built-ins is retired — `RETIRED_SKILLS` deletes it from the install dir at startup). Review engines (`review_engine_for(target)`) are always embedded skills, so a round can't die on an unresolvable skill after a full session spawn; a unit test pins engine ∈ `SKILLS`. Workflow sessions are **named by title + job** (`workflow_session_name(meta, slug, review_job(...))`: `Auth refactor · implement`, `Auth refactor · plan review r2`, `· explain`, `· answer PR comments`; untitled items fall back to `wf-<slug>`), so the sessions sidebar says what each agent is doing and for what. Per item, the **⚙ Settings tab** (per-item knobs + item facts) can switch to bare job names via `meta.bareSessionNames` — stored as the negative so serde's missing-field default and `WorkflowMeta::default()` agree on "prefixed" (a `default = "true_fn"` field silently reads false on struct-literal construction). **Every skill phase opens with an interactive-vs-autonomous question** (`AskUserQuestion` blocks safely — the human launched the session and is watching; the item is parked and "End round" unwedges) unless the kickoff pre-answers it with `Interactive: yes|no` — the review composer's three-way choice (ask in session / interactive / autonomous, recorded as `meta.review.interactive`, absent = ask) feeds that field. All three live in `SKILLS` (`skills/<name>/SKILL.md` via `include_str!` in `infrastructure::skills`) and are installed/refreshed under `<claude_dir>/skills/` at every startup of either binary, compare-then-write so unchanged content never rewrites; the embedded copy is the source of truth, and the install is **stamped and reported**: `.clash-skills.json` records the clash version + per-skill content hash of what was last written, `install_skills` returns a `SkillsReport` (updated / retired-removed / locally-edited-overwritten), the GUI toasts a non-noop report at boot (`get_skills_report`) and the TUI logs it — a clash upgrade that rewrites skills is visible, never silent. The GUI's ☰ Skills tab (`list_skills`/`get_skill` commands) renders every installed skill, badges clash-managed ones and shows the installing version.
- **The change-request note is the next round's prompt, so it gets a real composer.** `review.md`'s latest `## Iteration N` section is the first thing the `clash-workflow` skill reads, which makes that note the highest-leverage string in the pipeline — it was typed into a one-line `uiPrompt` where a newline was impossible. `wfComposeChangeRequest` (app.js) is one markdown composer for both plan-review and diff-review (previously two divergent inline prompts) and doubles as the round's launchpad: insertable **What to change / Why / Out of scope** template, findings insertable from **any** agent review round (round picker over `agentReviewRounds`/`roundFindings` in `wf-compose.js`), `renderMarkdown` preview of exactly what will land in `review.md`, the queued open annotations as **interactive rows** (uncheck to *park* — `AnnotationStatus::Parked`, kept but not `open`, so the agent contract skips it with no skill change; parking happens server-side in `workflow_request_changes` *before* the snapshot — plus jump-to-diff via `wfJumpToAnnotation`/`wfRevealAnnotation` and delete), an **After recording** group (record only, or launch the fix round now with interaction mode + executor-skill override → `ExecutorKickoff`), ⌘↵ to send, and an in-memory draft kept when the dialog is dismissed (not localStorage — that is documented as unreliable here, and a draft is not worth promising across a relaunch). The diff header's ↑/↓ buttons cycle open comments, expanding lazy-collapsed files on the way. The pure half — template, placeholder, annotation summary, submit rule — is `gui/dist/wf-compose.js` with `gui/tests/wf_compose.test.js`, per the `wf-diff.js` precedent; one of those tests loads the module's browser branch in a `vm` and asserts every global app.js reads is published, because a rename there fails at *click* time, not at boot, so the log still shows a healthy `frontend booted:` line. **Both targets submit through `workflow_request_changes`** (snapshot → review.md append → one meta write), so a plan-targeted round freezes `history/<NNN>/plan.md` like the diff path freezes `diff.patch` (a bare status write here was the bug that made plan revisions untraceable — `update_workflow_status` no longer accepts a note at all, the append is idempotent per iteration number so a crash-retry replaces its stale section instead of duplicating it, and a failed `git diff` aborts the round rather than freezing an empty `diff.patch`, except at `plan-review` where the plan is the artifact). Those frozen copies feed the **Timeline** sub-view (replaces the flat History list): one newest-first feed of change rounds (note + plan diff + frozen plan text + code diff; `get_workflow_timeline` returns `parse_review_iterations`/`all_agent_reviews` output, `get_workflow_history_plan` the frozen text, `get_workflow_plan_diff` the pairwise diff) interleaved with agent review rounds (verdict + published) — pure merge/order model in `gui/dist/wf-timeline.js` + `gui/tests/wf_timeline.test.js`. The item view also renders a **pipeline stepper** (where am I / what happened / what's left, per entry mode) whose pure model is `gui/dist/wf-pipeline.js` + `gui/tests/wf_pipeline.test.js`, same precedent.
- **Agent review rounds are a self-returning side-trip, and that is what makes them unbounded.** `reviewing` is entered from any state with a reviewable artifact parked on a human decision (`can_request_review`: plan-review / diff-review / pr-draft / pr-ready) and left by restoring `meta.review.returnStatus` — so round N+1 starts exactly where round N did, and the human can review as many times as they like without the item advancing. Modelling a review as a *stage* instead would have let it advance the pipeline, which is the one thing it must never do (approval is the human's). The target is **derived** (`ReviewTarget::for_status`), never asked — a plan review at diff-review has nothing to read; depth (`standard`/`deep`) and publish (`local`/`pr-comments`/`respond-pr-comments`) are the human's per-round choices, recorded in `meta.review` and repeated in the kickoff prompt so the reviewer can refuse impossible work before reading anything. Rounds run **interactively or autonomously — the human's call, made at launch or in-session**: absent a launch-time choice the skill's opening question asks, and in interactive rounds findings are triaged with the human in-session before they are written, fixes and PR posts are confirmed first, and dropped findings are recorded under `### Dismissed in triage` so later rounds don't re-raise them — a round applies nothing by itself; findings become work via *Request changes* (kept code findings are already open annotations; the composer's "Insert round N findings" button pastes plan findings into the note via the pure `latestAgentRoundFindings` in `wf-compose.js`). Those choices are surfaced as **one composer dialog** (`wfComposeReviewRound`, pure model in `gui/dist/wf-review.js` + `gui/tests/wf_review.test.js` per the `wf-compose.js` precedent) holding the round's whole shape on one screen — depth, findings destination (`local`/`pr-comments`) and the interaction mode (ask in session / interactive / autonomous → `interactiveParam`) — while `respond-pr-comments` is **its own action button** ("⇄ Answer PR comments", depth `standard`), not a composer choice: answering reviewers is a different job from producing a fresh review, and as the third option of a stacked second dialog it was invisible even to the person who asked for it. That button carries `meta.pr.unansweredComments` (replyless review-comment threads, counted by the pure `gh::count_unanswered_review_comments`, refreshed by `refresh_workflow_pr` under the same write-only-on-change discipline; the GUI's lazy PR poll includes `diff-review` items with a PR because review-only items park there), so a respond round's workload is visible without opening GitHub. Findings split by surface: code → `annotations.json` with `"author": "agent"` (so they enter the existing triage loop and one *Request changes* turns them into work), plan + verdict → append-only `agent-review.md` (a **separate** file from `review.md`, which is clash's record of human decisions — one file would make ownership ambiguous exactly where both sides write). Because approval is gated while `reviewing`, `cancel_workflow_review` + the "End round" button + the `agent_alive` cross-check are not niceties: they are the only way a dead reviewer doesn't wedge the item. `spawn_item_session` is shared by both launchers so a reviewer session is registered/named/status-stamped identically — an unregistered one would surface as a wild process. Three more properties earned the hard way (a round whose `respond-pr-comments` posted nothing, invisibly): `meta.review` is **never cleared** — it means "round in flight" only while `status == reviewing` and "most recent round" afterwards, so gate on the status, never on the block; round *outcomes* come from `agent-review.md` via the pure `latest_agent_review` parser (→ `WorkflowItem.lastAgentReview`, rendered as the outcome strip + hand-back toast, with `### Published` mandatory in every round's report); and publishing is recoverable after the fact (`publish_workflow_review` posts the latest round as one PR comment), because a publish decision bound only at launch forced a whole new round just to share an existing one. The PR states are not a dead end either: `pr-draft`/`pr-ready → changes-requested` exist because review feedback keeps arriving once a PR is up — and a fix round on an item with a PR **pushes** after committing (the branch is published; local-only commits leave the PR silently stale). **PR-identity errors recover in place**: commands needing a PR identity return machine prefixes (`no-pr:` / `pr-number-unknown:`) and the GUI's `wfPrRecovery` answers them by prompting for the PR URL, attaching it (`attach_workflow_pr` never demotes a `pr-ready` item) and retrying the action once; a review round needing a PR also offers "run locally instead". The general contract (pinned by a source test): an error caused by a data gap must let the human supply the datum and continue — never a bare alert.
- **Agent launches persist meta first, then spawn — and roll back on spawn failure.** Both launchers (`start_workflow_agent`, `start_workflow_review_agent`) generate the session id, write `meta.json` (session id + parked/working status + the `review` block), and only then spawn. The ordering is the crash-safety choice: "recorded but never spawned" surfaces the existing ⚠ relaunch / End-round affordances, while the old spawn-first order could leave a **live agent on an unrecorded item** — approval ungated, annotations unlocked, `cancel_workflow_review` refusing — with no recovery path. A failed spawn restores the pre-launch meta (keeping the worktree/branch, which exist on disk, so a retry never hits `branch-exists` on its own artifacts). The executor kickoff also carries `PR skill: <name>` when `workflows.pr_skill` is configured — the `pr` phase (and the implement phase's optional draft-PR step) must open PRs through that skill (e.g. `hivebrite-engineering:github-pr`) instead of raw `gh pr create`, so org house style rides along; the setting is a `PROPS` row surfaced in Settings → Workflows (`get_workflow_pr_skill`/`set_workflow_pr_skill`).

## Conventions

- **No IO in the reducer.** Effects are the only way the reducer communicates with the outside world.
- **Atomic writes everywhere.** Use `write_atomic()` for any file mutation to prevent corruption during concurrent access.
- **Lenient serde on all domain types.** Never fail on unknown/missing fields — use defaults and capture extras.
- **Each view is a trait impl.** `TableView` for list screens, `DetailView` for detail screens. Generic widgets in `tui/widgets/` render them.
- **Nested action enums.** `Action::Team(TeamAction::Create { .. })`, not flat variants. Each domain has its own sub-reducer.
- **Tests alongside code.** Unit tests in `#[cfg(test)]` modules within each file. Integration tests in `tests/`.

## Clean Architecture Principles

These rules must be followed on every change:

- **One core, two frontends.** Any feature must be implementable by both the TUI and the GUI (modulo genuine platform limits): business logic and persistence go through the shared core (`DataRepository`, effects, `session_refresh`), never duplicated in `gui/src-tauri/main.rs` or the TUI adapters. If a frontend needs a capability, add it to the port/effect layer first.
- **Infrastructure does not own business logic.** `backend.rs` loads and returns data — it does not sort, filter, or transform for presentation. Sorting, filtering, and display formatting belong in the Application or Adapter layers.
- **Computed display fields use `#[serde(skip)]`.** Fields derived at runtime (e.g., `worktree_project`) that are never in the on-disk JSON must use `#[serde(skip)]`, not `#[serde(default)]`. Follow the `repo_config` precedent.
- **Pure functions for testability.** When logic parses strings, formats output, or makes decisions, extract it into a pure function (no IO) and test it directly. Filesystem-touching wrappers should be thin. Example: `parse_gitdir_content()` (pure) wraps into `detect_worktree()` (reads file).
- **Domain port traits stay minimal.** Never leak infrastructure concerns (filesystem paths, watcher events, cache hints) into `DataRepository`. If the infrastructure layer needs an optimization API (e.g., cache invalidation), put it on the concrete struct (`FsBackend`), not the trait.
- **No dead code.** Do not leave unused functions, imports, or fields. If trait obligations force methods that are never called through the generic path (e.g., `SessionsTable::row()` — needed by `TableView` but bypassed by `render_sessions_table()`), document why with a comment.
- **DRY display helpers.** When the same formatting logic is needed in multiple views, create a single helper function (e.g., `worktree_display_from_cwd()`) rather than repeating the pattern at each call site.
- **Stable session ordering.** Sessions are sorted by section (Active/Pending/Done/Fail) then alphabetically by name inside `session_refresh::build_session_list()`. The backend returns unsorted data; sorting happens in the pure pipeline before atomic swap. Selection is stabilized by ID across refreshes.
- **Shadow-swap session refresh.** The session refresh pipeline builds a complete new session list in a staging `Vec<Session>` without touching `store.sessions`, then swaps atomically. If daemon IPC fails, running daemon-only sessions are preserved from the previous cycle. This prevents flickering.
- **Agent liveness cross-reference.** `DataStore::rebuild_all_members()` checks each agent's `is_active` against running sessions (CWD-based matching). Agents with no matching running session are marked inactive.
- **Delta subagent reloading.** `refresh_changed_subagents()` only reloads subagents for sessions whose status or subagent_count changed since the last refresh, avoiding N disk reads per refresh cycle.
- **Cache transparency.** `FsBackend`'s internal `SessionCache` is invisible to the `DataRepository` trait. Invalidation is driven by the FS watcher in `app.rs` via `invalidate_session_cache()`. On first load, everything is scanned; on subsequent loads, only dirty projects are re-parsed.

## Testing

- **Unit tests** (inline): reducer actions, serde parsing, navigation, input handling, atomic writes, CLI commands
- **Integration tests** (`tests/`): `data_layer_test.rs` (fixtures → DataRepository), `full_cycle_test.rs` (action→state→effect cycles)
- **Test fixtures** (`tests/fixtures/`): 5 teams (valid, empty, malformed, extra fields), 4 tasks, inbox messages
- **TestDataDir helper** (`tests/helpers/test_data_dir.rs`): copies fixtures to a temp dir for isolated tests

## Common Tasks

### Adding a new view
1. Create `src/adapters/views/my_view.rs` — impl `TableView` or `DetailView`
2. Add variant to `ViewKind` enum in `src/adapters/views/mod.rs`
3. Add navigation action in `src/application/actions/navigation.rs`
4. Handle in `renderer.rs` draw dispatch
5. Add keybinding in `input.rs`

### Adding a new action
1. Add variant to the appropriate action enum in `src/application/actions/`
2. Handle in `src/application/reducer.rs` — return appropriate `Effect`s
3. Map keyboard input in `src/adapters/input.rs`

### Adding a new effect
1. Add variant to `Effect` enum in `src/application/effects.rs`
2. Handle execution in `src/infrastructure/app.rs` `execute_effects()`

### Opening sessions externally (windowing)
- `o` opens the selected session in a pane (if terminal supports it) or tab/window
- `O` (Shift+O) opens ALL running sessions with smart layout (confirm dialog first)
- Layout: panes fill first (horizontal or vertical based on screen size), overflow to tabs
- Sessions opened externally show `⊞` prefix and cannot be reopened until closed
- Cleanup: when the external `clash attach` process exits, the indicator clears on next refresh
- Implementation: `src/infrastructure/windowing/terminal_spawn.rs` (spawn logic), `src/infrastructure/windowing/attach.rs` (attach client)

## Dependencies

Key crates: `ratatui` (TUI), `crossterm` (terminal events, TUI raw mode), `nix` (termios for attach raw mode, PTY), `tokio` (async), `serde`/`serde_json` (data), `notify-debouncer-full` (FS watching), `clap` (CLI args), `color-eyre`/`thiserror` (errors), `lru` (inbox cache), `tui-input` (text input widget), `chrono` (timestamps), `fuzzy-matcher` (filter mode).

## Gotchas

- **Config is read through `ConfigHandle`, never an owned `Config`.** A cloned handle is cheap and every clone observes a live reload; an owned copy cannot, which is why `Config::load()` no longer exists as a runtime accessor (it used to be called independently at five sites, so nothing could observe a reload). Writes are GUI-only and go through `set_json`/`reset_values`. Four properties are load-bearing and each replaced a real bug: unknown keys, comments and key order survive a save (writes edit the parsed `toml_edit` document and touch only changed keys, so a *newer* clash's settings aren't deleted by an older one); a no-op write doesn't rewrite the file (so a settings round-trip can't wake the watcher); an unparseable file **blocks writes by type** (`ConfigWriteError::Blocked` while `ConfigState::error` is set, so no call site can forget and overwrite it with defaults); and the whole read-modify-write runs under an advisory lock (`config.toml.lock`) with a re-read *inside* the lock, because `write_atomic` makes a write whole but not serialized — two instances would otherwise both read version N and the later one silently drops the earlier one's key. Full reference: `docs/configuration.md`.
- **A setting is one `PROPS` entry in `config/schema.rs`** — that single table drives defaults, validation, `--defaults`, the JSON Schema, the GUI blob migration and the GUI's live-apply hints, so adding a row is the whole job. `scope` decides the store: 8 settings are `Shared` (in `config.toml`, read by both frontends — the 7 migrated GUI keys plus `workflows.pr_skill`) and 21 are `GuiLocal` (xterm rendering + theme, which the TUI can never apply, so they stay in `gui-state.json`). A test pins the 28 *legacy blob keys'* split, so a new GUI setting without a schema entry fails the build instead of silently reverting to a default. `refit` marks the keys that change cell metrics and is the *only* discriminator that lets a config reload enter the expensive refit path.
- **The 7 shared settings are deliberately absent from the GUI's `gui-state.json` blob.** Keeping a copy there would let a stale blob overwrite a hand-edited `config.toml` on the next boot — and WKWebView's localStorage is not `HOME`-isolated, so a copy *there* can outlive an isolated-`HOME` test run. Two things prevent it: `guiLocalSettings()` filters shared keys out of what gets persisted, and only the **disk** blob may seed the one-shot migration (`loadWorkspaces` passes `migratable: false` for the localStorage fallback).
- **Watcher path comparisons must tolerate symlinks.** `notify` reports the path the OS *resolved*, so a root reached through a symlink never prefix-matches the configured spelling and every event under it is silently dropped — the failure mode is a directory that just quietly stops auto-refreshing, with nothing in the log. `RoutedWatcher` therefore watches both the configured and the canonical spelling of each root, and `ConfigHandle::is_config_path` compares the *resolved parent* rather than the whole path. This is not hypothetical: it made live config reload a no-op under a `/tmp` HOME (macOS resolves `/tmp` → `/private/tmp`), and would do the same for a dotfile-managed or cloud-synced `Application Support`.
- **The GUI has one `RoutedWatcher`, not one `FsWatcher` per directory.** It covers `~/.claude/projects`, scratch, workflows and the config dir, routing each batch to its root by longest-prefix match (so a scratch dir nested under the Claude data dir isn't also treated as a session change). It was three separate watchers with three independent debounce windows; config would have made four, and the reload burst-coalescing needs one place to live. Repointing a directory in Settings calls `rebuild_watcher` — it rebuilds wholesale rather than adding a watcher. Routing happens on the watcher's own thread, **not** in a spawned task: `rebuild_watcher` is called from Tauri's `setup`, which runs on the main thread with no Tokio runtime entered, so a `tokio::spawn` there aborts the app at launch with "there is no reactor running".
- `main.rs` uses `mod` (private), `lib.rs` uses `pub mod` (public for tests). Both declare the same 4 layers.
- The `notify-debouncer-full` error type lives at `notify_debouncer_full::notify::Error`, not `notify::Error`.
- Raw strings containing `#` in JSON values (like hex colors) need `r##"..."##` delimiters.
- Inboxes are lazy-loaded with LRU(3) eviction — they're only fetched when navigating to the inbox view.
- Agent attach uses suspend-and-resume: save state → restore terminal → spawn `claude --resume` → reclaim terminal on exit.
- External session opening (`o`/`O`) uses the `windowing` module: pane-capable terminals (tmux, iTerm, WezTerm, Kitty) get split panes; others get tabs/windows. Sessions opened externally are tracked in-memory via `externally_opened` and shown with `⊞` prefix.
- `clash attach <id>` is a lightweight subcommand for external panes — it connects to the in-process daemon of a running clash app (TUI or GUI), not a standalone daemon. Multiple instances may run simultaneously, each with its own `daemon-<pid>.sock`; attach probes live sockets and picks the instance that owns the session.
- The attach loop reads from `/dev/tty` (not fd 0) to avoid racing with crossterm's internal reader thread. The standalone client uses `nix::sys::termios` for raw mode instead of crossterm to prevent crossterm's reader from being initialized.
- Ctrl+B detach supports three terminal encodings: raw `0x02`, Kitty CSI u (`ESC[98;5u`), and xterm modifyOtherKeys (`ESC[27;5;98~`). iTerm2 uses the xterm format.
- `--debug` flag enables debug-level logging; the header shows a `DEBUG` indicator when active.
- Tauri 2 frontend APIs are permission-gated: `gui/src-tauri/capabilities/default.json` must grant `core:default` (includes `core:event:allow-listen`) or every `listen()` in the GUI frontend fails as a silent unhandled rejection — no `pty-output` ever reaches xterm and terminals render blank.
- wry's WKWebView does not implement native `alert`/`confirm`/`prompt` (silent no-ops) — use the in-app `uiConfirm`/`uiPrompt`/`uiAlert` dialogs in `gui/dist/app.js`.
- In-page **HTML5 drag-and-drop** (the scratch tree's move-by-drag) only fires if the window sets `"dragDropEnabled": false` in `tauri.conf.json`. Tauri v2 defaults it to `true`, which registers the OS/WKWebView file-drop handler that swallows `dragstart`/`dragover`/`drop` inside the webview — so the drag code runs but no drop ever lands (scratches silently won't move). Safe to disable because clash consumes no OS file-drop events. The scratch DnD itself lives in `buildNoteRow`/`wireNoteDropTarget`/`moveNote` (folders are drop targets; the `#notes-list` container is the root drop target), calling the `move_scratch` Tauri command directly.
- The bare-binary WKWebView's localStorage is not reliably persisted — durable GUI state (workspaces) goes through `save_gui_state`/`load_gui_state` to `gui-state.json` (atomic write) in the clash app-support dir.
- The embedded browser panel is one native child webview per tab (`Window::add_child`, tauri `unstable` feature, labels `embedded-browser-<n>`), stacked over `#browser-slot`; switching tabs hides/shows webviews, and the frontend reports the slot rect to ALL tabs on every layout change (`syncBrowserBounds` in `fitAll`). In-app DOM (dialogs, menus) cannot render above it.
- Child-webview coordinates ≠ DOM coordinates on macOS: the window uses a full-size content view, so in windowed mode WKWebView insets the main webview's page content by the title-bar height (~32px) while the native view spans the full window. Browser-tab webviews positioned with raw `getBoundingClientRect` values land a title-bar height too high and cover the pane's chrome strip (invisible in fullscreen, where the inset is 0). `browser_coord_offset()` measures the main webview's frame + `safeAreaInsets` live and every `browser_open`/`browser_set_bounds` adds it.
- In-app context menus **and every dialog/modal** must call `hideBrowserWebviews()` when opening and `fitAll()` on close — native browser webviews paint over all DOM, so an unhidden webview covers them. z-index cannot help: the webview is not in the DOM's stacking context at all, which makes the symptom misleading (a modal that "opens behind the GitHub panel" looks like a z-index bug and is not one). The `.dialog-backdrop` builders (`uiConfirm`/`uiPrompt`/`uiAlert`/`uiChoice`, `wfComposeChangeRequest`, `pickFontFamily`) and `showNewSessionModal` all pair the two; a new dialog that forgets is invisible only when a browser tab happens to be open, so it passes a casual test.
- **clash ships no macOS menu bar, so nothing dispatches ⌘C/⌘X/⌘V/⌘A to a text field.** On macOS those key equivalents reach a WKWebView input via the standard Edit-menu items; with no Edit menu, ⌘A does not select and ⌘C copies nothing — which reads as "the URL bar is broken". `handleInputClipboard` (a **capture-phase** document listener, because every dialog's own keydown handler calls `stopPropagation()`) implements the four against the backend clipboard, skipping xterm's `.xterm-helper-textarea` so terminals keep their own handling. Adding a real Edit menu is the tempting alternative and is deliberately not taken: a menu-level Copy claims ⌘C app-wide and would preempt `attachCustomKeyEventHandler`, where the selection is canvas-based and a native Copy would copy nothing. All copying goes through the one `copyText()` helper — `navigator.clipboard` is often absent in the bare WKWebView, so `navigator.clipboard?.writeText(…)` fails silently.
- **Never select-all in an `<input>` on the `focus` event.** mousedown focuses before the pointer settles, so the ensuing mouseup collapses the selection to a caret and a drag has nothing to extend — the field becomes unselectable by hand while looking fine. Gate on a mousedown flag and select in `mouseup` instead (the browser URL bar's own behaviour: click selects all, drag keeps the drag, Tab still selects all).
- Every async action button goes through `busyButton()` (labelled buttons; `spinButton()` is the icon-button sibling), wired centrally in `renderWfActions`'s `add()` so a new action cannot ship without feedback. The click-lock is load-bearing, not cosmetic: a second click on an in-flight "Create draft PR" opens a second PR.
- Never call `Webview::url()` on an embedded browser tab — wry's macOS impl unwraps WKWebView's `URL` property, which is nil until the first navigation commits; the panic hits the tao event loop thread and aborts the app (and replays on every launch via the persisted tab in `gui-state.json`). `browser_get_url` reads the property via `with_webview` + objc2 with a nil check instead.
- Don't feed `data:` URLs to the embedded browser — tauri rejects them at webview creation without the `webview-data-url` cargo feature (not enabled), and WKWebView silently drops multi-MB ones. Serve generated pages via `register_uri_scheme_protocol` instead (the local diff intentionally lives in an in-app tab, not the browser — the browser picker opens the GitHub diff).
- PTY children get `TERM=xterm-256color` + `COLORTERM=truecolor` defaults **only when TERM is missing or `dumb`** (Finder/Dock launches inherit launchd's bare env). A real terminal's values are never overridden, so Claude Code keeps its native colors in both the GUI and the TUI. Same "fill the blanks" pattern for locale: `session.rs` sets `LC_CTYPE` (macOS `UTF-8`, else `C.UTF-8`) **only when `LC_ALL`/`LC_CTYPE`/`LANG` are all unset** — otherwise a Finder/Dock launch runs the child under the `C`/POSIX locale and it misdecodes multibyte UTF-8 *on input* (a pasted/typed em dash `—` → `‚Äî` mojibake), even though output looks fine (frontends always decode UTF-8). Decision is the pure `default_lc_ctype()` (unit-tested); set before the `env_vars` loop so a repo-config locale still wins.
- `claude --resume <id>` **forks the conversation**: it writes a NEW transcript (fresh session id) while hook payloads keep reporting the *resumed* id — so unlike `/clear` (which fires SessionStart with the new id and re-keys `sessions.json` via the hook), a resume leaves the registry stale and the next restart would reopen the pre-fork conversation. The linkage lives inside the forked transcript (its hook entries embed `"session_id":"<resumed-id>"`): `registry::chase_resume_forks` walks that chain (newest match wins, sidechains skipped), `heal_registry_forks` re-keys the whole registry at startup of both binaries, and every resume site uses `resolve_latest_conversation` + `record_resumed_conversation` instead of the bare `resolve_resume_id`.
- Corollary of the re-key above: **a conversation id is not a stable identifier, so anything that persists one must resolve it forward.** The GUI persists them twice per workspace — pane slots *and* session ownership (`w.sessions` in `gui-state.json`) — and both must move together. Resolving only the panes was a real bug: an owned-but-not-open session whose conversation forked kept the pre-fork id in `w.sessions`, that id was pruned as "gone" after 3 refreshes, and its current id (owned by nobody) resurfaced under **UNASSIGNED** on every relaunch — a session the user never launched, reappearing forever. The two guards live in `gui/dist/ws-ownership.js` (pure, unit-tested via `node --test "gui/tests/*.test.js"`): `persistedSessionIds` feeds `resolve_session_ids` **panes + ownership** at restore, and `ownershipTransfers`/`pruneOwnership` make the refresh sweep *transfer* ownership to the resolved id instead of dropping it (a failed resolve defers the prune a tick rather than guessing "dead"). UNASSIGNED is meant to hold only sessions this GUI genuinely doesn't own yet — e.g. ones the TUI or another instance started.
- Wild claude processes are dynamically associated with a conversation: exact argv/fd evidence first, otherwise the latest-modified conversation in the process cwd (`latest_session_for_cwd`), re-evaluated each scan. `a` (TUI) / row click (GUI) = one confirm → kill outside process → `--resume` attach under the daemon.
- Log file (`~/Library/Application Support/clash/clash.log`) appends across restarts and auto-rotates after 24h (configurable via `CLASH_LOG_RETENTION_HOURS`).
- The GUI terminals set `macOptionIsMeta: true`, which alone would make brackets/braces untypeable on international Mac layouts (AZERTY types `{`/`[` with Option). Merely bypassing xterm (returning false from the custom key handler) does NOT fix it: WKWebView fires no keypress for Option combos and xterm's input-event fallback drops insertText preceded by a keydown (`!e.composed || !this._keyDownSeen`). The handler in `createTerminal` (gui/dist/app.js) must send the composed character to the PTY directly via `send_input`; Alt+letter still goes through xterm as Meta while the "⌥ sends Esc (Meta)" setting is on (when off, letters are direct-sent too).
- GUI terminal selection/copy requires `macOptionClickForcesSelection: true` on the xterm config. Claude Code enables mouse tracking (`?1000h`/`?1006h`), so xterm reports plain drags to it as mouse events and never selects text — making ⌘C copy nothing (or a garbled partial selection); this surfaced as "copy/paste doesn't work". With the flag, ⌥-drag forces a real selection (the native iTerm2 convention; xterm's `_shouldForceSelection` is `isMac ? altKey && macOptionClickForcesSelection : shiftKey`). It is mouse-only, so it does not interact with `macOptionIsMeta` / typing ⌥-composed glyphs. PTY I/O is byte-faithful end to end in *transport* (input: `send_input` → base64 `Request::Input` → raw PTY write; output: base64 → `Uint8Array` → `term.write`, which decodes UTF-8 and buffers split sequences), so mojibake is never introduced in transit. Two separate real bugs produced garbled chars: (1) the broken selection copying a partial cell run, fixed by the flag above; and (2) the PTY child running under the `C` locale and misdecoding pasted/typed UTF-8, fixed by the `LC_CTYPE` default in `session.rs` (see the PTY-env gotcha). The TUI attach needs no equivalent: it is raw passthrough, so the host terminal owns selection/copy/paste (⌥-drag in iTerm2, bracketed paste forwarded through `/dev/tty`).
- GUI session **reload** (⟳, next to the `✕` on section headers, on every session row/tab, and in the context menus) hot-restarts a session on the newest `claude` binary: `reloadSession(sid)` = `stash_session` (kill, keep resumable) → `dropTerminal` if open → `openSession` (which resumes the *latest* conversation id via `resolve_resume_id`, so no id is passed around by the frontend). It composes existing core ops — no new Tauri command. The section-level `reloadAll` and the per-row/tab buttons skip **actively-working** sessions (`isActivelyWorking`: status ∈ Thinking/Prompting/Waiting/Starting) because a turn in flight has no persisted id yet; reloading one of those individually first asks via `uiConfirm`. Wild rows get no reload (take-over is their action). No TUI equivalent yet — the crosses/icons are GUI-only.
- GUI split panes are resizable: `#terminal-host` is a CSS grid and `renderPanes` drives `gridTemplateColumns/Rows` from per-workspace `w.colFracs`/`w.rowFracs` (in `fr`), reset to equal whenever the grid shape changes (pane add/remove) or a single cell shows (zoom/one pane). Draggable `.pane-gutter` overlays sit at the internal track boundaries — positioned by `repositionGutters` from the cumulative fractions (not by reading pane layout), so `fitAll` (also the window-resize handler) repositions them. Dragging redistributes the fraction between the two adjacent tracks (min ~0.15fr each). Fractions persist in `gui-state.json`; `renderPanes` validates length + positivity and resets on mismatch, so a stale layout never yields a collapsed track.
- GUI panes clip their terminal (`.pane { overflow: hidden }` in `gui/dist/style.css`). FitAddon sizes rows from the **CSS** cell height (`rows = floor(availableHeight / cssCellHeight)`), but xterm renders each row rounded to **device** pixels, so `rows × renderedRowHeight` can exceed the container by a sub-row sliver. Neither `.pane`, `.term-wrap`, nor `.xterm` clips by default, so that excess `.xterm-screen` painted *past the pane's bottom edge* — and the excess scales with row count, so it was worst in the tallest terminal: a **single title-less pane** (no `.pane-title`, so it fills the whole grid cell). On a Retina Mac (fractional cell height, dpr 2) that pushed Claude's bottom input line out of the window — reported as "when only one tab is open, the bottom goes out of the window." `overflow: hidden` on `.pane` clips at the grid-cell (= window) boundary; xterm's own `.xterm-viewport` (`overflow-y: scroll`, absolute-positioned inside `.xterm`) still handles scrollback, so nothing is lost — only the sub-pixel sliver of the last row is trimmed.
- GUI terminals render with xterm's **WebGL renderer** (`gui/dist/vendor/addon-webgl.js`, `@xterm/addon-webgl@0.18.0` — the build matching the vendored `@xterm/xterm@5.5.0`; UMD global `WebglAddon`). The default DOM renderer repaints cells as styled `<span>`s and, under Claude Code's rapid streaming (spinners, progressive tokens), leaves stale/half-refreshed glyphs — reported as "not native, badly refreshed text." WebGL draws the whole grid to one GPU canvas per frame. It's loaded in `createTerminal` **after** `term.open(el)` (the addon needs the element mounted), inside a try/catch, and wires `onContextLoss(() => webgl.dispose())` — disposing reverts that terminal to the DOM renderer, so a lost/evicted GL context (WKWebView backgrounding, GPU pressure, or the browser's ~16-context cap when many panes are open) degrades gracefully instead of blanking. Each `Terminal` gets its own GL context, so the fallback is the safety net for context exhaustion.
- GUI terminal links (OSC 8 hyperlinks via `linkHandler.activate`, and plain-text URLs via the regex `registerLinkProvider`) both route through `openLink(uri)`, gated by the three-way `state.settings.linkOpen` setting (`ask` | `embedded` | `external`, default `ask`; a `<select>` in the SETTINGS panel). `ask` pops `uiChoice({message, detail, choices})` — a sibling of `uiConfirm`/`uiPrompt` that returns the picked value (or null) — offering "In clash" (embedded browser panel) vs "System browser" (`open_external`). Non-http(s) schemes (`mailto:`/`tel:`/`file:`) always go to the OS regardless of the setting. Legacy persisted `embedLinks: true/false` migrates to `embedded`/`external` in `applyWorkspacesData`.
- The update **Restart** button must `await flushWorkspaces()` before `invoke("restart_app")`. `restart_app` calls `app.restart()`, which re-execs the process WITHOUT firing any window/webview teardown events — so the `blur`/`pagehide`/`beforeunload`/`visibilitychange` listeners that normally persist "where we were" never run on this path. Skipping the explicit flush leaves `gui-state.json` only as fresh as the last 250ms-debounced save, so sessions/layout come back stale after an update ("sessions are not saved at the last conversation"). The session side is already covered separately by `restart_app`'s `stash_and_wait`; this is specifically the frontend workspace-state flush.
- Self-update (`update.rs`) is symlink-aware and name-aware: it canonicalizes targets before replacing (so `/usr/local/bin/clash-gui` → `Clash.app/Contents/MacOS/clash-gui` updates the bundle binary, not the link), installs the running binary first and the sibling at its existing canonical location, and on macOS bumps the bundle's Info.plist version + re-signs. Replacing the symlink itself would leave Finder/Dock launches permanently stale.
- Apps launched from Finder/Dock inherit launchd's minimal `PATH` (no `~/.local/bin`), so spawning `claude` fails with ENOENT. Both binaries call `env_path::adopt_login_shell_path()` at startup: it queries the user's interactive login shell (rc-file PATH exports included) with a 3s timeout, falls back to well-known bin dirs, and no-ops when PATH already has home-relative entries (i.e. launched from a real shell).
- GUI theming is one table (`THEMES` in `gui/dist/app.js`) feeding two consumers: the CSS custom properties in `:root` (chrome) and `TERM_THEME` (xterm). Both must move together or a switch leaves half the window in the old palette. Rules therefore must never hardcode a colour — `--bg-raised` (menus/toasts/code), `--on-accent` (text on an accent/red fill, derived from the accent's luminance), `--scrim` and `--shadow-*` (a 55%-black shadow reads as dirt on a light theme) exist so the light themes work without per-rule overrides; `:root.theme-light` covers what a colour can't express. `TERM_THEME` is a `let`, read when a terminal is constructed and reassigned by `applyTheme`, which also pushes `term.options.theme` to open terminals and clears the WebGL texture atlas (it caches glyphs at the old colours). A theme omitting `ansi` keeps xterm's built-in palette — clash dark does, so its terminals render exactly as before the theme system existed.
- GUI settings are declarative: a new one is a row in `index.html`, a default + a validated load line in `applyWorkspacesData` (`numSetting` for numbers), a line in `syncSettingsUi`, and one `bindNumberSetting`/`bindChoiceSetting` call. Passing `option:` live-applies the value to every open terminal as an xterm option (`applyTermOption`); add `refit: true` when it changes cell metrics (font/line-height/letter-spacing) so cols/rows are recomputed. Terminal options must also be added to the `new Terminal({…})` block or they only apply to already-open terminals. Verify any xterm option name against `gui/dist/vendor/xterm.js` before wiring it — a typo is silently ignored by xterm.
- The GUI font picker's family list is the **union** of `list_font_families` (AppKit `NSFontManager.availableFontFamilies`, hopped to the main thread via `run_on_main_thread` + a channel — AppKit is main-thread-only, and a Tauri command runs off it) and a curated set probed with `document.fonts.check`. Neither is sufficient alone: macOS does **not** enumerate `SF Mono` (clash's default font) even though the webview renders it, and the curated list only holds fonts someone thought to name. Monospace detection is a canvas width measurement (`iiii…` vs `WWWW…`), not a name regex — on a stock Mac a name match finds 4 families, only 2 of which are monospace, and misses Menlo/Monaco/SF Mono entirely.
- The frontend logs one `frontend booted: …` line to clash.log at the end of its boot IIFE (via `dlog`/`gui_log`). WKWebView has no visible console in a release build, so without that marker a JS error during boot is indistinguishable from a backend problem — the log looks healthy and the only symptom is a blank window. When smoke-testing the GUI, that line is the positive signal to grep for.
- `HOME=<dir> clash-gui` isolates everything clash writes (`Config::clash_data_dir`, `dirs::data_dir`) — useful for testing against a throwaway state. What it does *not* isolate is WKWebView's `localStorage`, which resolves the real user home: the frontend's `loadWorkspaces` falls back to it when `gui-state.json` is absent, so an isolated instance can still read the real user's persisted settings blob. Disk state stays isolated; treat localStorage as shared.
